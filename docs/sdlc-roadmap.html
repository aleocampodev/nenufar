🔄 1. Máquina de Estados del Pedido (Order Lifecycle)

Transiciones del pedido desde su captura en la web hasta la entrega física y cobro manual por Shirley vía WhatsApp.

stateDiagram-v2
    [*] --> Carrito: Clienta añade joyas en /shop
    Carrito --> Formulario: Pasa a /pedidos/enviar
    
    state "Pendiente (pending)" as Pending {
        [*] --> GuardadoEnDB: submitOrderAction crea Order en Payload
        GuardadoEnDB --> NotificadoTelegram: Envía HTML a @pedidos_nenufar
        NotificadoTelegram --> ContactoWhatsApp: Shirley abre chat de WhatsApp con clienta
    }
    
    Formulario --> Pending: Envío de pedido
    
    Pending --> Confirmed: Pago recibido (Nequi/Daviplata)\nShirley usa bot o /admin
    Pending --> Cancelled: No responde / Desiste / Sin stock
    
    state "Confirmado (confirmed)" as Confirmed {
        [*] --> EmpaqueYPreparacion: Shirley alista la joya y empaque
    }
    
    Confirmed --> Shipped: Paquete despachado con guía\nShirley usa bot: 'marcarEnviado' o /admin
    Confirmed --> Cancelled: Reembolso solicitado antes de despacho
    
    state "Enviado (shipped)" as Shipped {
        [*] --> EnRuta: Guía enviada por WhatsApp
        EnRuta --> Entregado: Paquete recibido
    }
    
    Shipped --> [*]: Pedido completado
    Cancelled --> [*]: Pedido cerrado sin venta

🤖 2. Máquina de Estados del Bot de Gestión (Claude Agent SDK Runtime)

Ciclo de vida interno de una petición en el endpoint /telegram/webhook con el SDK de agentes y el proxy LiteLLM.

stateDiagram-v2
    [*] --> Recibido: POST /telegram/webhook (Telegram Update)
    
    state "Validación de Seguridad" as Auth {
        Recibido --> VerificarSecreto: Comprobar header X-Telegram-Bot-Api-Secret-Token
        VerificarSecreto --> Rechazar403: Secreto inválido
        VerificarSecreto --> VerificarChatId: Secreto válido
        VerificarChatId --> Ignorar200: chat_id != TELEGRAM_ADMIN_CHAT_ID (No es Shirley)
        VerificarChatId --> VerificarDedupe: chat_id == Shirley
        VerificarDedupe --> IgnorarDedupe200: update_id ya procesado
        VerificarDedupe --> InicializarContexto: Mensaje nuevo válido
    }
    
    state "Ejecución Claude Agent SDK" as SDKLoop {
        InicializarContexto --> CargarToolsMCP: createSdkMcpServer([buscarProducto, pedidosPendientes])
        CargarToolsMCP --> EnviarPrompt: query(prompt, systemPrompt, model)
        
        state "Bridge LiteLLM & Groq" as Bridge {
            EnviarPrompt --> ProxyLiteLLM: Anthropic Messages API (:4000)
            ProxyLiteLLM --> GroqAPI: OpenAI API (drop_params: true)
            GroqAPI --> EvaluarRespuesta: Retorna Tool Call o Texto Final
        }
        
        EvaluarRespuesta --> EjecutarTool: Modelo solicita Tool Call
        EjecutarTool --> LocalAPI: payload.find() / payload.update()
        LocalAPI --> RetornarObservacion: Datos reales de PostgreSQL
        RetornarObservacion --> EnviarPrompt: SDK inyecta resultado
        
        EvaluarRespuesta --> FinalizarRespuesta: Modelo genera respuesta final de texto
    }
    
    FinalizarRespuesta --> ResponderTelegram: sendTelegramReply(chatId, reply)
    ResponderTelegram --> [*]: 200 OK
    Rechazar403 --> [*]: 403 Forbidden
    Ignorar200 --> [*]: 200 OK (Silencioso)
    IgnorarDedupe200 --> [*]: 200 OK (Silencioso)

⚡ 1. Flujo de Compra y Notificación (Storefront Web → Telegram → WhatsApp)

Secuencia completa de cómo se genera la orden en la tienda y cómo Shirley coordina el pago manual.

sequenceDiagram
    autonumber
    actor C as Compradora (Web)
    participant F as Storefront Next.js (/pedidos/enviar)
    participant SA as Server Action (submitOrderAction)
    participant P as Payload CMS / Postgres
    participant TG as Telegram Channel (@pedidos_nenufar)
    actor S as Shirley (Dueña)
    actor WA as Compradora (WhatsApp)

    C->>F: Llena formulario (Nombre, WhatsApp, Dirección, Consentimiento Ley 1581)
    C->>SA: Envía pedido (Submit)
    SA->>SA: Validar idempotencia (hash de carrito + contacto)
    SA->>P: payload.create('orders', { status: 'pending', items, total, ... })
    P-->>SA: Order ID #42 creado en PostgreSQL
    SA->>TG: sendTelegramMessage(HTML con datos del pedido)
    TG-->>S: Notificación en el celular: "🌸 Nuevo pedido #42 de María..."
    SA-->>F: Redirección a /pedidos/enviar/confirmacion?orderId=42
    F-->>C: Muestra pantalla de éxito ("Shirley te contactará por WhatsApp")
    
    Note over S,WA: Coordinación de pago humano
    S->>WA: Shirley escribe por WhatsApp: "Hola María, recibí tu pedido #42..."
    WA->>S: Envía comprobante de pago por Nequi/Daviplata

⚡ 2. Flujo de Consulta del Bot de Shirley (Claude Agent SDK + LiteLLM + Groq)

Secuencia de ejecución de herramientas sobre Payload CMS respondiendo a Shirley en Telegram.

sequenceDiagram
    autonumber
    actor S as Shirley (Telegram)
    participant W as Webhook (/telegram/webhook)
    participant RSA as runShirleyAgent()
    participant SDK as Claude Agent SDK (query)
    participant LLM as LiteLLM Proxy (:4000)
    participant G as Groq API (Llama 3.3 70B)
    participant T as SDK Tools (createShirleyTools)
    participant DB as Payload Local API / Postgres

    S->>W: Mensaje: "¿Qué pedidos tengo pendientes?" (chat_id: 123456)
    W->>W: Validar X-Telegram-Secret & chat_id == ADMIN_CHAT_ID
    W->>RSA: runShirleyAgent(texto, { payload, chatId, userName })
    RSA->>SDK: query({ prompt, mcpServers: { nenufar: tools }, model: 'nenufar-bot' })
    
    SDK->>LLM: POST /v1/messages (Anthropic API format)
    LLM->>LLM: drop_params: true (elimina output_config)
    LLM->>G: POST /chat/completions (OpenAI format, model: llama-3.3-70b-versatile)
    G-->>LLM: Responde: tool_call -> pedidosPendientes()
    LLM-->>SDK: Traduce a Anthropic Tool Use
    
    SDK->>T: Invoca handler de pedidosPendientes()
    T->>DB: payload.find({ collection: 'orders', where: { status: 'pending' } })
    DB-->>T: Retorna lista de órdenes pendientes ([#42, #43])
    T-->>SDK: Content: "Pedidos pendientes: #42 ($180.000 COP), #43 ($90.000 COP)"
    
    SDK->>LLM: POST /v1/messages (con resultado de la tool)
    LLM->>G: POST /chat/completions
    G-->>LLM: Responde texto final: "Shirley, tienes 2 pedidos pendientes: #42 y #43 🌸"
    LLM-->>SDK: Traduce a Anthropic Message Text
    SDK-->>RSA: Retorna texto final
    RSA-->>W: reply string
    W->>S: sendTelegramReply(chatId, reply)

🛠️ Las 24 Skills de Ingeniería Instaladas (`.agents/skills/`)

Cada skill representa un protocolo de ingeniería senior para ejecutar tareas con rigor en cada fase del SDLC.

Fase 1 & 2 · Definición
interview-me
Entrevista interactiva pregunta a pregunta para extraer la verdadera intención antes de planificar o codificar.
Fase 1 & 2 · Definición
spec-driven-development
Redacción de especificaciones funcionales y criterios de aceptación antes de escribir código.
Fase 1 & 2 · Definición
idea-refine
Refina ideas crudas mediante pensamiento divergente y convergente estructurado.
Fase 3 · Diseño
api-and-interface-design
Diseño de contratos de API estables, interfaces tipadas y fronteras entre módulos.
Fase 3 · Diseño
documentation-and-adrs
Registro formal de Decisiones de Arquitectura (ADRs) documentando el 'por qué'.
Fase 3 · Diseño
security-and-hardening
Validación estricta de inputs, autenticación de webhooks y prevención de vulnerabilidades OWASP.
Fase 4 · Construcción
incremental-implementation
Entrega de cambios en rebanadas verticales delgadas y comprobables paso a paso.
Fase 4 · Construcción
frontend-ui-engineering
Construcción de interfaces de usuario accesibles (WCAG), responsivas y con tokens de marca.
Fase 4 · Construcción
source-driven-development
Fundamentación de decisiones técnicas en la documentación oficial de los frameworks.
Fase 5 · Pruebas
test-driven-development
Desarrollo guiado por pruebas (Red-Green-Refactor) con Vitest y Playwright.
Fase 5 · Pruebas
doubt-driven-development
Revisión adversarial en contexto limpio de decisiones críticas antes de aceptarlas.
Fase 5 · Pruebas
code-review-and-quality
Revisión de calidad en 5 ejes antes de mergear cualquier cambio a ramas base.
