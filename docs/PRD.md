# PRD-001: MVP Scope - Agento (Agentic Showcase & Intrinsic CRM)

## Status
Accepted

## Purpose
Define the functional requirements, interface behaviors, user journeys, and acceptance criteria for the Agento Minimum Viable Product (MVP). This document ensures that engineering builds a strict two-phase conversational funnel, eliminating passive navigation and limiting the AI to act as a deterministic conversion vehicle, not a free-text chatbot.

---

## Users
1. **The Buyer:** Seeks zero friction, immediate visual gratification, and a secure transaction. They do not browse; they declare intent and react to visual components.
2. **The Operator (Admin):** Interacts exclusively with Payload CMS to add inventory under a strict taxonomy and consult paid orders. Demands that the software requires no manual updates of commercial states.

---

## User Journeys (Critical Flows)

### Journey 1: Discovery and Freezing (Web)
1. The Buyer enters the Next.js web application.
2. They view a minimalist canvas with a text input and dynamic "Intent Chips" (e.g., "Decor", "Gift").
3. Upon clicking a chip or typing an intent, the system streams an ephemeral interface (Generative UI).
4. The Buyer interacts with React buttons inside that UI (material selection, adding custom engraving).
5. The Buyer clicks "Buy via WhatsApp".
6. The system generates an immutable code (e.g., `AX-892`) and transfers the Buyer to the WhatsApp app.

### Journey 2: Rehydration and Closing (WhatsApp)
1. The Buyer sends the autogenerated code via WhatsApp.
2. The system intercepts the message, retrieves the cart, and greets the buyer, confirming the product, material, and extras selected.
3. The Agent requests shipping logistics data.
4. The Buyer provides the city or address.
5. The Agent dispatches a unique payment link (Wompi/Stripe) and temporarily locks the conversation.
6. Once payment is confirmed by webhook, the system generates the Dispatch Sheet in the CMS.

---

## Functional Requirements

### 1. Web Interface (Edge Frontend)
* **Intent Chips:** Primary filters (Category, Occasion) defined in the CMS must render as quick-action buttons below the main input.
* **Generative UI (Vercel AI SDK):** The LLM model must invoke tools to stream interactive components (Product Cards) to the client. Free-text paragraph responses about the catalog are prohibited.
* **Ephemeral UI (Configurator):** The product component must contain React state logic so that the user can configure options (e.g., requesting an engraving) via booleans and structured text fields.

### 2. The Handoff Bridge
* **State Mutation:** Pressing the purchase button on the ephemeral UI must execute a *Server Action* that inserts a Zod-validated `JSONB` payload into the `handoff_sessions` PostgreSQL table.
* **Integrity Validation:** Before generating the code, the system must confirm that the product remains in `available: true` status in Payload CMS.

### 3. Autonomous Agent (WhatsApp)
* **Pre-LLM Guardian:** The webhook must use traditional logic (Regex) to identify session codes (`AX-\d{3}`). If matched, the AI is not invoked; the server sends a fixed template message.
* **Conditioned Upselling:** If the web intent was generated for a product with the `isCustomizable: true` flag, the LLM on WhatsApp has the commercial mandate to offer customization for the defined additional cost.
* **Payment Delivery:** The agent must be able to invoke the payment link generation *Tool* and halt its persuasion phase immediately after delivering it.

### 4. Intrinsic CRM (Payload CMS)
* **Automated Technical Sheet:** A *Route Handler* will listen to payment gateway webhooks. Upon a `charge.succeeded` event, it will create an immutable entry in the CMS `Orders` collection with the exact breakdown (Name, Product, Customization, Address).

## Non-Functional Requirements (Architecture and UI/UX)

* **Strict Ruthless Design:** The web interface must adhere to an institutional, imperative design.
  * Typography: *Space Grotesk*.
  * Geometry: Flat and sharp edges (0-2px `border-radius`). No decorative animations.
  * Color Palette: Deep Navy Blue background (`#0A192F`), Technical Yellow accents and CTAs (`#F2C94C`), high-contrast typography.
* **Serverless Performance:**
  * Streaming the first chunk of Generative UI on the web must not exceed **1.5 seconds**.
  * Transactional response on WhatsApp must not exceed **3.0 seconds**.
* **Cost Limiter:** The Vercel AI SDK will operate with `maxSteps: 2` to avoid infinite tool-calling loops that deplete the budget.

---

## States and Edge Cases (Session State Machine)

The `handoff_sessions` table will dictate LLM behavior based on the following immutable states:

| State | Context / AI Behavior |
| :--- | :--- |
| `PENDING` | The code was created on the web, but the customer has not written on WhatsApp. Lifespan: 24 hours. |
| `QUALIFYING` | The customer reached out. The agent is permitted to discuss materials, logistics, and upsell. |
| `CHECKOUT_PENDING` | Logistics agreed. The agent generated the payment link. The *System Prompt* changes: offering new products is prohibited. |
| `CLOSED` | Payment gateway webhook successfully received. The LLM turns off. Static automated responses ("Order in preparation"). |
| `ABANDONED` | More than 24 hours have passed since `CHECKOUT_PENDING` without payment. The LLM turns off for this session. |

**Edge Case 1:** The user initiates a valid session code but then starts sending voice notes, memes, or out-of-domain questions to WhatsApp.
**Resolution:** The *System Prompt* includes a non-negotiable fallback. If the user deviates from the logistical/commercial context more than twice, the model invokes the forced closing tool: *"I am only trained to process your craft order. Let me know when you are ready to proceed"*, and releases the resources.

## Acceptance Criteria

1. **Web Acceptance:** A user can type "I'm looking for something wooden," receive an interactive product card, configure an engraving, and get a URL to WhatsApp in under 3 seconds without the LLM responding with conversational prose.
2. **State Acceptance:** The `JSONB` generated in the handoff matches 1:1 with the Zod schema derived from the Payload CMS collections, without TypeScript compilation errors.
3. **WhatsApp Acceptance:** When sending the valid code via WhatsApp, the Next.js webhook returns the greeting with the exact product referenced in the `JSONB` without invoking OpenAI text inference for that initial greeting.
4. **Closing Acceptance:** The system is capable of silently updating the state from `CHECKOUT_PENDING` to `CLOSED` upon receiving a ping from the test gateway, and the record appears formatted in the Payload panel.

---

## Analytics / Tracking
* The count of tokens consumed per session (Input/Output) will be stored within the `handoff_sessions` log to audit deviations from *Unit Economics*.
* Retention rate will be tracked: Percentage of sessions that remain in `PENDING` (clicked on the web but never wrote on WhatsApp) versus those that move to `QUALIFYING`.

---

## Out of Scope
* 3D modeling of crafts on the Frontend.
* Purchase history for recurring users (Web authentication).
* Multiple simultaneous payment gateways (the MVP will operate exclusively with the chosen primary provider).
